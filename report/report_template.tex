\chapter{Introduction}

\section{Background and Motivation}

Embedded systems used for real-time data acquisition often need to process large amounts of sensor data while meeting strict timing requirements. Multi-core processors help meet these demands by allowing computational tasks to run in parallel. However, making effective use of multiple cores requires proper task distribution and synchronization, especially in systems where predictable execution time and responsiveness are important.

Sensor data may also contain unwanted variations, such as sudden spikes, bursts of abnormal readings, or dropouts caused by electromagnetic interference, sensor faults, or changes in operating conditions. Identifying and removing these outliers is important for obtaining reliable results during statistical analysis. Combining this filtering process with data sorting increases the computational workload. In a Real-Time Operating System (RTOS), these operations must be handled efficiently without affecting the system's ability to respond to inter-process communication (IPC) requests and hardware interrupts.

\section{Project Objectives}

This project focuses on developing a real-time client-server system using the QNX RTOS and deploying it on a Raspberry Pi 4. The system is designed to transfer unsorted floating-point time-series data from a client to a server in blocks of at least 64 KB for processing. The server performs two main operations:

\begin{enumerate}
    \item \textbf{Parallel Sorting:} A parallel Merge-Sort algorithm is implemented using multiple POSIX worker threads. Mutexes and condition variables are used to coordinate thread execution and synchronization during the sorting and merging stages.

    \item \textbf{Rolling Median Filtering:} A robust rolling median filter (Hampel filter) is applied to identify and remove outliers from the time-series data. The filter uses local median and median absolute deviation (MAD) values to detect abnormal readings while preserving the underlying signal.
\end{enumerate}

After processing, the server notifies the client through a QNX pulse event containing the calculated median and a descriptor specifying the relevant memory offset. The processed arrays remain in shared memory, allowing the client to access the results without requiring another complete data transfer.

\section{Workload and Dataset}

The system is evaluated using a synthetic dataset generated offline with PyBaMM, a Python-based battery modelling package. The dataset contains battery measurements, including current, voltage, and temperature, representing a simulated discharge cycle. To evaluate the ability of the filtering algorithm to detect abnormal readings, controlled noise and outliers are introduced into the data.

The dataset includes the following types of corruption:

\begin{itemize}
    \item \textbf{Gaussian Noise:} Additive white Gaussian noise is introduced into the measurements to simulate variations in sensor readings. Example noise levels include 2 mV for voltage and 8 mA for current.

    \item \textbf{Impulsive Outliers:} Outliers are introduced in the form of sudden spikes, consecutive bursts, and stuck readings. These outliers are introduced at random and occur at a rate of 1.5\%. A ground-truth mask is also maintained to identify the injected outliers and evaluate the filtering performance.
\end{itemize}

This dataset provides a controlled environment for evaluating the sorting and filtering algorithms under different data conditions. It also allows the results to be compared against the known locations of the injected outliers.

Communication between the two processes follows a strict sequence to ensure data integrity and asynchronous notification. 
\begin{enumerate}
    \item The client connects to the server using \texttt{name\_open}.
    \item The client sends a 64 KB block using an IOV message (\texttt{MsgSendv}).

    \item Once processing is complete, the server sends a QNX pulse back to the client.
    \item The client retrieves the result descriptor using a fetch message.
\end{enumerate}

\section{Virtual Sensor}
\label{sec:sensor}

There is no physical sensor on the bench, so the service is fed by a module that
replays a recording with the behaviour of a live device. Values arrive one sample
at a time, in frames, on a clock the module keeps itself rather than at the speed
of the host. The purpose is not convenience: with the sensor behind this
interface the client and the rest of the pipeline can be developed and tested
exactly as they will run against hardware, and a real device can replace the
module later without changing anything downstream.

\subsection{Addressing a sample in either layout}

Both layouts are headerless little-endian \texttt{float32}, and both are read by
one expression, where \texttt{next} is the sample the sensor is about to deliver:

\begin{equation}
  \texttt{value} = \texttt{window}\bigl[(\texttt{next} - \texttt{window\_first})
  \times \texttt{stride} + \texttt{offset}\bigr]
  \label{eq:sensor-address}
\end{equation}

A planar file is \texttt{stride} 1 and \texttt{offset} 0, so sample $i$ is float
$i$. An interleaved file is four floats per record  time, voltage, current,
temperature  so sample $i$ of the voltage channel is float $4i + 1$: record 1
is float 5, byte 20 of the file. The three unused floats of each record are read
from disk and discarded; a channel other than the selected one is never returned.
Figure~\ref{fig:sensor-layout} shows both cases.

\subsection{The read-ahead window}

The recording is not loaded whole. Reads pass through a sliding window of
\texttt{window\_samples} records  4096 by default, widened when the caller's
frame is larger  which is refilled as the reader advances. In the real pipeline
the block loader asks for block-sized frames, so the window becomes 16\,384
records: 64\,KiB of a planar file or 256\,KiB of an interleaved one, in one call
to \texttt{fread}. A caller reading one sample at a time therefore sees exactly
the same values as a caller reading whole blocks, a property the tests use as an
independent check.

The refill condition is the three-part test in Listing~\ref{lst:sensor-read}: the
window is empty, the reader was rewound behind it, or it has walked past the end.
The loop applies the test before every sample, so no case can read stale data.

        if (!s->cfg.loop)
            break;                      /* end of the recording */
        s->next = 0;                    /* a live sensor never stops */
    }

        s->next < s->window_first ||    /* rewound behind the window */

\subsection{Frames, blocks and the sensor's clock}

A device read returns a frame, not an arbitrary amount of data:
\texttt{sensor\_read} delivers at most \texttt{frame\_samples} samples, and
\texttt{sensor\_read\_frame} delivers exactly one frame except at the end of a
recording. Assembling a 64\,KiB payload is the client's concern, which is what
\texttt{sensor\_read\_block} does: it calls \texttt{sensor\_read} until the block
is full, so the aggregation sits on the client side of the boundary rather than
inside the device.

The clock is arithmetic rather than a system timer. The timestamp of the next
sample is \texttt{sensor\_index} $\times 10^9 / \texttt{rate\_hz}$ nanoseconds,
computed from a counter of samples delivered, so after 600 samples at 100\,Hz it
is exactly 6\,s however fast the host runs; in loop mode the counter keeps
advancing across the wrap, as a sensor that never stops would.
\texttt{sensor\_read\_paced} adds a wait after each read so the stream holds the
configured rate. That wait and the monotonic clock behind it are the only
platform-specific code in the project  \texttt{clock\_gettime} and
\texttt{nanosleep} on QNX, with one shim for the host build  and its resolution
is a millisecond, so pacing is meaningful up to roughly 500\,Hz.

\section{Block Loader}
\label{sec:block-loader}

The block loader connects the virtual sensor to the client by organizing the incoming sensor samples into fixed-size blocks for transmission. Each block contains 16,384 samples, as defined in the code using the name "\texttt{PROTO\_BLOCK\_SAMPLES}". Since each sample is a 32-bit floating-point value, the total block size is 65,536 bytes (64 KiB). The loader also prepares a descriptor containing the metadata required to identify and validate each block.

\subsection{Handling Multiple File Layouts}

The dataset stores recordings in two formats: planar and interleaved. In the planar format, each channel is stored separately, whereas the interleaved format stores multiple channel values together in each record. The loader must account for these differences while ensuring that the correct data is selected for each protocol channel.

In the interleaved format, each record follows the order \texttt{[time\_s, voltage\_V, current\_A, temperature\_K]}. This order must be mapped correctly to the enumeration used by the protocol. To avoid selecting the wrong signal during processing, the loader handles this mapping through a dedicated function. For instance, voltage is stored at index 1, while current is stored at index 2.

% SOURCE: block_loader.c, function block_loader_channel_offset()
\begin{lstlisting}[caption={Mapping protocol channels to interleaved file offsets using \texttt{block\_loader\_channel\_offset}}, label={lst:loader-offset}]
int block_loader_channel_offset(proto_channel_t channel)
{
    switch (channel) {
    case PROTO_CHANNEL_TIME:        return 0;
    case PROTO_CHANNEL_VOLTAGE:     return 1;   /* not 2: see the header note */
    case PROTO_CHANNEL_CURRENT:     return 2;
    case PROTO_CHANNEL_TEMPERATURE: return 3;
    default:                        return -1;
    }
}
\end{lstlisting}

The loader also configures the virtual sensor's frame size to match the protocol block size using \texttt{cfg.frame\_samples = PROTO\_BLOCK\_SAMPLES}. This allows \texttt{sensor\_read\_block()} to read the required 16,384 samples in a single operation for a full block, rather than processing each sample individually. This approach keeps the data-loading process straightforward and reduces the overhead associated with repeated read operations.


\subsection{Zero-Padding and the Descriptor}

The recording length may not always be an exact multiple of 16,384 samples. In such cases, the final block contains fewer valid samples than the protocol's fixed block capacity. Since the complete 64 KiB buffer is transmitted between processes through the QNX message-passing mechanism, the unused portion must be initialized before transmission. Otherwise, it could contain stale memory contents and produce inconsistent results between executions.

The loader sets all unused sample positions in the final block to zero, so the buffer is predictable even when the recording ends partway through a block. It then fills the block descriptor (sequence number, valid sample count, first sample index, rate, channel, and checksum). The checksum uses FNV-1a hash algorithm and covers only the valid samples, excluding the zero-padded tail.

% SOURCE: block_loader.c, function block_loader_next()
\begin{lstlisting}[caption={Zero-padding the final block and populating its descriptor in \texttt{block\_loader\_next}}, label={lst:loader-pad}]
    /* Zero the unused tail of a short final block. */
    if ((uint32_t)got < PROTO_BLOCK_SAMPLES) {
        memset(&block->samples[got], 0,
               (size_t)(PROTO_BLOCK_SAMPLES - (uint32_t)got) * sizeof(float));
    }

    memset(desc, 0, sizeof(*desc));
    desc->sequence     = (uint32_t)l->sequence;
    desc->samples      = (uint32_t)got;
    desc->first_sample = l->samples;
    desc->rate_hz      = l->rate_hz;
    desc->channel      = (uint32_t)l->channel;
    desc->checksum     = proto_checksum(block->samples,
                                        (size_t)got * sizeof(float));

    l->sequence++;
    l->samples += (uint64_t)got;
    return got;
}
\end{lstlisting}

\section{Parallel Merge-Sort}
\label{sec:mergesort}

Sorting a block is the service's one genuinely parallel computation, and it is the
step where a mistake is hardest to see: a wrong sort still returns numbers of the
right count. The implementation is therefore built around two properties that can
be checked rather than argued. The output does not depend on how many workers ran,
and the plan the workers actually executed is reported, so a run can be shown to
have taken the parallel path rather than the serial one.

\subsection{The pool and the plan}

The threads are created once per process by \texttt{ms\_pool\_create}  one per
online CPU by default, four on the Raspberry Pi 4, capped at
\texttt{MS\_MAX\_THREADS} (64)  and they wait on a condition variable when there
is nothing to do. Nothing is created or destroyed per block.

Each sort splits the one array it was given according to how much work a worker
needs to be worth waking:

\begin{equation}
  k = \min\!\left(\left\lfloor \frac{n}{1024} \right\rfloor,\ \texttt{nthreads}\right),
  \qquad \texttt{part} = \left\lceil \frac{n}{k} \right\rceil
  \label{eq:merge-plan}
\end{equation}

so a 16\,384-sample block on four workers becomes four partitions of 4096. Phase
0 posts one partition task per slice; each worker sorts its slice with the
ordinary single-threaded merge sort, writing into its own region of one scratch
buffer. What comes back is four sorted runs, not one sorted block. The merge
phases then halve the number of runs  merge adjacent pairs, swap which buffer
is read and which is written, repeat  until a single run covers the array.
Figure~\ref{fig:merge-plan} shows the shape of a block on four workers: three
rounds, seven tasks.


\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{merge_sort.pdf}
    \caption{The plan for one 64\,KiB block on four workers. Phase 0 sorts four
    partitions, each into its own slice of the scratch buffer; each later phase
    merges adjacent runs and writes the other buffer, so the answer alternates
    between the caller's array and the scratch. A phase cannot begin until every task

\end{figure}


\subsection{The merge, and why the answer is stable}

Two sorted runs become one by looking at the front of each and taking the smaller,
which is the whole of the merge:

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[caption={The merge step. The comparison is \texttt{<=}, so on
a tie the value from the left run goes first.}, label={lst:merge-runs},
basicstyle=\ttfamily\footnotesize]
static void merge_runs(const float *a, size_t na,
                       const float *b, size_t nb, float *out)
{
    size_t i = 0;
    size_t j = 0;
    size_t k = 0;

    while (i < na && j < nb)
        out[k++] = (a[i] <= b[j]) ? a[i++] : b[j++];
    while (i < na)
        out[k++] = a[i++];
    while (j < nb)
        out[k++] = b[j++];
}
\end{lstlisting}
\end{minipage}

That one character, \texttt{<=} rather than \texttt{<}, is what makes the sort
\emph{stable}: equal values keep the order in which they arrived. Stability is
what makes the result independent of the thread count. A different partition
count changes \emph{when} two equal values meet, and the tie rule decides the
same way whichever side they come from, so one worker and eight workers produce
byte-identical output. The test suite asserts exactly that, for one, two, three,
five and eight workers.

\subsection{The barrier between phases}

Each phase's tasks go into one shared array and the workers claim them from a
queue. The phase boundary is a barrier on completion, not a delay:

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[caption={\texttt{post\_phase()}: publish a round's tasks, then
block until every one of them has been counted as done.}, label={lst:post-phase},
basicstyle=\ttfamily\footnotesize]
static void post_phase(mergesort_pool_t *p, unsigned ntasks)
{
    pthread_mutex_lock(&p->lock);
    p->ntasks     = ntasks;
    p->next_task  = 0;
    p->tasks_done = 0;
    pthread_cond_broadcast(&p->work_ready);
    while (p->tasks_done < p->ntasks)
        pthread_cond_wait(&p->phase_done, &p->lock);
    pthread_mutex_unlock(&p->lock);
}
\end{lstlisting}
\end{minipage}

The worker side is the other half of the same protocol: take the lock, wait on
\texttt{work\_ready} until a task index is available, copy that index out, and
release the lock \emph{before} running the task  the sort itself never runs
under the lock. When it finishes it takes the lock again, increments the count and
the task counter, and the worker that reaches \texttt{ntasks} signals
\texttt{phase\_done}. The caller wakes, and only then posts the merges that read
what those tasks wrote. There is no sleep anywhere, so a slow machine simply takes
longer; it cannot produce a different order. The buffers and the task array are
changed only between phases, which is after every task has been counted, so a
worker never reads a task that is being rewritten.

\subsection{Refusals, and the plan line}

Two decisions keep the parallel path honest. Inputs below
\texttt{MS\_PARALLEL\_MIN} (4096 values) are sorted single-threaded, because
waking a pool costs more than the sort saves at that size, and
\texttt{ms\_sort} refuses a second concurrent call on the same pool with $-1$
rather than corrupting the shared round state  one pool sorts one array at a
time.

The plan is recorded as it happened, not as it was intended: the statistics count
partitions, merge phases and tasks actually executed. That record is what makes
the parallelism checkable. ``1 partition, 0 merge phases, 1 task'' cannot come out
of a four-worker run, so the plan line is proof that the parallel path was taken,
whereas the elapsed time alone would not distinguish a fast serial sort from a
parallel one.

\section{Rolling Median Filter (Hampel Filter)}

The server implements a rolling Hampel filter to detect and suppress outliers in time-series sensor data while preserving samples that follow the local signal trend. Unlike a conventional moving-median filter that replaces every sample with the median of its neighbourhood, the Hampel filter replaces a sample only when it deviates significantly from the local median.

\subsection{Window-Based Median and MAD Calculation}

For a sample \(x_i\), the filter extracts a sliding window of odd width \(w\), centred on the current sample. The local median is calculated as

\[
m_i = \operatorname{median}
\left(
x_{i-h},\ldots,x_i,\ldots,x_{i+h}
\right),
\qquad h=\frac{w-1}{2}.
\]

The median absolute deviation (MAD) measures the spread of the samples around this local median:

\[
\operatorname{MAD}_i =
\operatorname{median}_{j\in W_i}
\left|x_j-m_i\right|.
\]

The robust estimate of the local standard deviation is obtained using the scaling factor 1.4826:

\[
\sigma_i^{*}=1.4826\,\operatorname{MAD}_i.
\]

A sample is classified as an outlier if

\[
|x_i-m_i| > \lambda \sigma_i^{*},
\]

where \(\lambda\) is the configurable threshold. The implementation uses a default threshold of 4.0. When the condition is satisfied, the output sample is replaced by the local median; otherwise, the original sample is retained.

\subsection{Filter Configuration and Boundary Handling}

The filter supports odd window widths from 3 to 31 samples, with a default width of 9. A width of 9 considers up to four neighbouring samples on each side of the current sample. A larger window can detect wider bursts of abnormal samples, but it increases computational cost and may smooth legitimate short-duration variations.

The filter processes samples in their original time order. Since sorting destroys temporal order, the server maintains separate data paths for sorting and filtering rather than applying the rolling filter to the sorted array.

For block-based processing, neighbouring samples from adjacent blocks are supplied as context. This prevents artificial discontinuities at block boundaries and makes block-wise filtering equivalent to filtering the complete signal, provided the required context is supplied. At the beginning and end of the complete recording, the window is clipped to the samples that actually exist.

The implementation is deterministic and does not allocate memory dynamically during filtering. Each local window is ordered using insertion sort, allowing the median and MAD to be calculated without a separate general-purpose sorting operation.

\section{Client Implementation}
\label{sec:client}

The client acts as the orchestrator of the pipeline. Its responsibilities include reading the recording, preparing 64 KiB blocks, submitting them to the server, and retrieving the results. Because the system relies on asynchronous events, the client must set up its own receiving channel using \texttt{name\_attach()} before it even connects to the server. If the server is not yet running, the client waits rather than failing immediately.

\subsection{Connection Deadline}
A strict requirement of the project is that the client must tolerate the server starting slightly late. The client implements a 10-second deadline by repeatedly calling \texttt{name\_open()} with a 250 ms \texttt{nanosleep} delay between attempts. If the server appears within this window, the connection succeeds and the wait time is logged. If the deadline expires, the client prints a descriptive error and exits cleanly, avoiding an indefinite hang.

% SOURCE: client.c, function connect_to_server()
\begin{lstlisting}[caption={Retrying the server connection with a 10-second deadline}, label={lst:client-retry}]
static int connect_to_server(const char *name, uint64_t deadline_ns,
                             uint64_t *waited_ns, int *attempts)
{
    uint64_t start = now_ns();
    int      tries = 0;

    for (;;) {
        struct timespec pause;
        uint64_t        elapsed;
        int             coid = name_open(name, 0);

        tries++;
        if (coid != -1) {
            if (waited_ns != NULL) *waited_ns = now_ns() - start;
            if (attempts != NULL)  *attempts  = tries;
            return coid;
        }
        elapsed = now_ns() - start;
        if (elapsed >= deadline_ns) {
            if (waited_ns != NULL) *waited_ns = elapsed;
            if (attempts != NULL)  *attempts  = tries;
            return -1;  /* errno is the last name_open failure */
        }
        pause.tv_sec  = 0;
        pause.tv_nsec = (long)CONNECT_RETRY_NS;
        (void)nanosleep(&pause, NULL);
    }
}
\end{lstlisting}

\subsection{Pipeline Orchestration and Block Preparation}
The client drives the local data pipeline before interacting with QNX. Before the transmission loop begins, it calls \texttt{block\_loader\_open()} to initialize the virtual sensor and prepare the file layout. Inside the loop, it calls \texttt{block\_loader\_next()} to read the 16,384 samples from disk, zero-pad the final block if necessary, and generate the block descriptor. Only after this local preparation is complete does the client package the header using \texttt{proto\_submit\_prepare()} and trigger the IPC mechanisms. The complete execution flow is shown in Figure~\ref{fig:client-flow}.

\begin{figure}[htbp]
\centering
\includegraphics[width=\textwidth]{pipeline_flowchart.pdf}
\caption{Execution flow of the Client. The client loops through the blocks, utilizing QNX message passing. Once the recording ends (EOF), it performs a global sort, filters the data, writes the output files, and exits.}
\label{fig:client-flow}
\end{figure}

\subsection{Two-Part IOV Submission}
To transmit a 64 KiB block, the client avoids copying the payload into a single, massive message buffer. Instead, it uses an Input/Output Vector (IOV) to send the message in two separate parts: the small \texttt{proto\_submit\_t} header and the 64 KiB \texttt{proto\_block\_t} payload. 

The client arms a reply deadline using \texttt{TimerTimeout} and calls \texttt{MsgSendv()}. This allows the QNX kernel to transfer the header and data directly from their respective memory locations. The client then blocks until it receives the server's acknowledgement (ACK), verifying that the message type, job ID, and checksum status are all correct.

% SOURCE: client.c, inside the main block loop
\begin{lstlisting}[caption={Submitting a block using a two-part IOV}, label={lst:client-iov}]
        iov_t send_iov[2], reply_iov;
        
        /* ... prepare submit and block ... */
        
        SETIOV(&send_iov[0], &submit, sizeof(submit));
        SETIOV(&send_iov[1], &block, sizeof(block));
        SETIOV(&reply_iov, &ack, sizeof(ack));
        
        arm_reply_deadline("submit");
        
        if (MsgSendv(server_coid, send_iov, 2, &reply_iov, 1) == -1) {
            perror("client: MsgSendv submit");
            goto cleanup;
        }
        
        if (ack.type != PROTO_MSG_ACK || ack.job_id != job_id ||
            ack.status != PROTO_OK) {
            fprintf(stderr, "client: submit %u rejected: %s\n",
                    job_id, proto_status_str(ack.status));
            goto cleanup;
        }
\end{lstlisting}

\subsection{Completion Pulse Handling}
Because the server processes the block asynchronously, it sends a QNX pulse when the work is done. The client waits for this pulse using \texttt{MsgReceive()} with a 5-second timeout. A QNX pulse can only carry a 32-bit value; however, an IEEE 754 float is also exactly 32 bits. The server bit-casts the calculated median directly into the pulse value. The client extracts this 32-bit integer and bit-casts it back into a float, receiving the median instantly without needing a separate message round-trip.

\subsection{Shared Memory Retrieval}
After receiving the pulse, the client sends a fetch message to get the result descriptor, which contains the exact byte offsets of the sorted and filtered arrays. 

Instead of transferring 128 KiB (two 64 KiB arrays) back through message passing, the client maps the server's named shared memory object as read-only. It validates the header and the job ID to ensure the slot hasn't been overwritten, and then reads the arrays directly using the supplied offsets. Finally, it recalculates the FNV-1a checksums of the arrays in memory to prove that the data was not corrupted in transit.

\subsection{Final Verification and Output}
Once all blocks have been offloaded (the loader returns 0), the client's work is not yet done. It performs a local verification and post-processing phase:
\begin{itemize}
    \item It sorts the entire recording locally using a serial merge-sort to verify that its global median matches the median the server sent in the final pulse.
    \item It runs a continuous rolling median filter(Hampel) over the entire raw recording to ensure that block boundaries do not cause artifacts in the final output.
    \item It writes the processed arrays to disk as \texttt{raw.bin}, \texttt{sorted.bin}, and \texttt{filtered.bin}, alongside a \texttt{medians.csv} file containing the per-block statistics.
\end{itemize}

\section{Server Implementation}
\label{sec:server}

The server handles the processing of incoming data blocks. It runs as a QNX channel server, where it receives client requests, checks their validity, and assigns the processing tasks to a pool of worker threads. This allows the server to accept new requests without waiting for the sorting and filtering of previous blocks to finish.

\subsection{Initialization and Resource Allocation}

Before starting the receive loop, the server initializes the resources required for processing. It calls \texttt{shm\_region\_create()} to create and map a named shared memory region that stores the sorted and filtered arrays. Next, \texttt{ms\_pool\_create()} creates the worker thread pool used for parallel merge sort, with the default configuration using one thread per CPU core. Finally, \texttt{name\_attach("sortmed")} registers the server under its service name and creates the QNX channel through which it receives client requests.

\subsection{Two-Stage Reception and Validation}

Since each data block is 64 KiB, the server checks the request header before accepting the entire payload for processing. It first uses \texttt{MsgReceivev()} to receive the 48-byte \texttt{proto\_submit\_t} header. The server checks the protocol version and validates the filter width using \texttt{proto\_submit\_valid()}. It then calls \texttt{proto\_submit\_verify()} to verify the block checksum.

If any validation step fails, the server returns an appropriate error status using \texttt{MsgReply()} and skips further processing of that request. This helps avoid unnecessary work on invalid input.

% SOURCE: server.c, inside the main MsgReceivev loop
\begin{lstlisting}[caption={Receiving and validating the request header}, label={lst:server-receive}]
        rcvid = MsgReceivev(attach->chid, riov, 2, &info);
        /* ... */
        if (type == PROTO_MSG_SUBMIT) {
            proto_ack_t ack;
            memset(&ack, 0, sizeof(ack));
            ack.type = PROTO_MSG_ACK;
            ack.job_id = submit.job_id;

            if (submit.version != PROTO_VERSION) {
                ack.status = PROTO_ERR_VERSION;
                (void)MsgReply(rcvid, 0, &ack, sizeof(ack));
                continue;
            }
            if (!proto_submit_valid(&submit)) {
                ack.status = PROTO_ERR_ARGUMENT;
                (void)MsgReply(rcvid, 0, &ack, sizeof(ack));
                continue;
            }
            if (!proto_submit_verify(&submit, &block)) {
                ack.status = PROTO_ERR_CHECKSUM;
                (void)MsgReply(rcvid, 0, &ack, sizeof(ack));
                continue;
            }
\end{lstlisting}

\subsection{Early Acknowledgement}

The server does not keep the client waiting until all the processing is complete. In QNX, the \texttt{rcvid} identifies a received message and is used to reply to that request. Once the reply is sent, that receive ID can no longer be used for the same request.

After validating the submission, the server therefore sends an acknowledgement (ACK) before the computational work begins. The client can then continue with its workflow and wait for a separate completion pulse, while the server proceeds with processing the submitted block.

\subsection{Block Processing and Function Calls}

After acknowledging the request, the server processes the data block through \texttt{process\_submit()}. The function copies the input into a separate array so that the original time order is preserved for filtering. It then performs the following operations:

\begin{enumerate}
    \item Copies the input samples into a separate array using \texttt{memcpy()}, preserving the original data order.
    \item Calls \texttt{ms\_sort()} to sort the copied samples using the parallel worker pool.
    \item Calls \texttt{median\_filter\_block()} to apply the Hampel filter to the original time-ordered samples.
    \item Uses \texttt{proto\_checksum()} to calculate the FNV-1a checksums of the sorted and filtered arrays.
    \item Stores the result metadata, including the median, filter width, number of outliers, and checksums, in the \texttt{proto\_result\_t} structure.
\end{enumerate}

% SOURCE: server.c, inside process_submit()
\begin{lstlisting}[caption={Sorting, filtering, and preparing the block results}, label={lst:server-process}]
    /* Preserve the original sample order for filtering. */
    memcpy(sorted, block->samples, n * sizeof(float));

    /* Sort the block using the parallel worker pool */
    if (ms_sort(pool, sorted, n) != 0) return -1;

    /* Apply the Hampel filter to the original time-ordered block */
    if (median_filter_block(&cfg, NULL, 0, block->samples, n, NULL, 0,
                            filtered, &outliers) != 0)
        return -1;

    /* Store the result metadata and checksums */
    job->result.median = median_of_sorted(sorted, n);
    job->result.filter_width = cfg.width;
    job->result.outliers_removed = outliers;
    job->result.sorted_checksum = proto_checksum(sorted, n * sizeof(float));
    job->result.filtered_checksum = proto_checksum(filtered, n * sizeof(float));
\end{lstlisting}

\subsection{Global Run Aggregation}

In addition to processing individual blocks, the server calculates the median of the complete recording. To do this, it maintains a global sorted array that is updated as each block is processed. The function \texttt{run\_merge\_block()} merges each block's sorted samples into this array. When a submission carries the \texttt{PROTO\_SUBMIT\_LAST} flag, the server calls \texttt{run\_publish()} to store the final \texttt{proto\_run\_t} descriptor in shared memory, including the global median.

\subsection{Asynchronous Pulse Notification}

After processing a block, the server notifies the client that the results are ready. Since the original request has already been acknowledged, its \texttt{rcvid} is no longer available for notification. The server instead uses \texttt{name\_open()} to obtain a connection to the client's registered channel, \texttt{sortmed-client}.

The server converts the block median into a 32-bit pulse value using \texttt{proto\_float\_to\_pulse()}. This allows the median to be included in the completion pulse, along with a code derived from the job ID. The server sends the pulse using \texttt{MsgSendPulse()}. Once the notification attempt is complete, it closes the connection using \texttt{name\_close()}.

% SOURCE: server.c, resolving the client and sending the pulse
\begin{lstlisting}[caption={Sending a completion pulse to the client}, label={lst:server-pulse}]
            float pulse_median = jobs[free_index].result.median;
            int coid = name_open(CLIENT_NAME, 0);

            if (coid == -1 ||
                MsgSendPulse(coid, SIGEV_PULSE_PRIO_INHERIT,
                             PROTO_PULSE_DONE + (int)submit.job_id,
                             proto_float_to_pulse(pulse_median)) == -1) {
                perror("sortmed-server: completion pulse");
            }
            if (coid != -1) {
                name_close(coid);
            }
\end{lstlisting}

\section{QNX IPC Mechanisms}
\label{sec:qnx-ipc}

The system uses three QNX inter-process communication (IPC) mechanisms to exchange requests, notify the client, and transfer the processed results. Each mechanism serves a different purpose in the processing pipeline.

\begin{itemize}
    \item \textbf{Message Passing (IOV):} The client uses \texttt{MsgSendv()} to send the 48-byte header and the 64 KiB data block using separate I/O vector entries in a single call. This allows the header and payload to be provided from different memory locations without first combining them into a single buffer.

    \item \textbf{QNX Pulses:} Since processing takes several milliseconds, the server sends an acknowledgement (ACK) after validating the request instead of keeping the client waiting for the entire operation. Once processing is complete, it uses \texttt{MsgSendPulse()} to notify the client. The calculated median is encoded in the 32-bit pulse value field.

    \item \textbf{Shared Memory:} Sending the sorted and filtered arrays back through message passing would add unnecessary data transfer overhead. The server instead writes both arrays to the named shared memory object \texttt{/dev/shmem/sortmed-results}. The client maps this region as read-only and accesses the results directly, avoiding the need for another large message transfer.
\end{itemize}

\section{End-to-End Pipeline Execution}
\label{sec:pipeline}

The complete pipeline combines the client, server, worker threads, and shared memory to process each 64 KiB data block. The client submits the data and receives an acknowledgement before the server begins the main computation. Once processing is complete, the server notifies the client using a QNX pulse. This allows the two sides to handle submission and processing without keeping the original request open until the results are ready.

Figure~\ref{fig:pipeline-execution} shows the overall data flow for a single block.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{pipeline_general.pdf}
    \caption{End-to-end execution of a 64 KiB data block. Message passing handles requests and control signals, shared memory stores the processed arrays, and QNX pulses notify the client when processing is complete.}

\end{figure}

\subsection{Phase 1: Local Preparation and Submission}

The process starts on the client side, where \texttt{block\_loader\_next()} reads up to 16,384 samples from the dataset. If the final block contains fewer samples, the remaining positions are zero-padded. The client then calculates the FNV-1a checksum and prepares the request using a 48-byte \texttt{proto\_submit\_t} header and a 64 KiB \texttt{proto\_block\_t} payload.

The client submits both parts using \texttt{MsgSendv()}. On the server side, \texttt{MsgReceivev()} receives the request, after which the server checks the protocol version, filter width, and checksum. If the request passes validation, the server sends an acknowledgement (ACK) to the client.

The ACK is sent before the main processing begins. This allows the client to continue its execution and wait for a completion pulse rather than remaining blocked until sorting and filtering are finished. The original request is therefore completed separately from the later notification of the results.

\subsection{Phase 2: Computation and Publication}

After acknowledging the request, the server processes the submitted block using \texttt{process\_submit()}. The main operations are:

\begin{enumerate}
    \item The raw samples are copied into a designated shared memory slot, preserving their original time order.
    \item The server calls \texttt{ms\_sort()} to sort the samples using the worker thread pool. The sorted data is stored separately from the raw samples.
    \item The function \texttt{median\_filter\_block()} applies the Hampel filter to the original time-ordered data and stores the filtered output in another slot.
    \item The server calculates the output checksums and fills the \texttt{proto\_result\_t} descriptor with the result metadata.
\end{enumerate}

After preparing the results, the server obtains a connection to the client's registered channel and sends a completion pulse using \texttt{MsgSendPulse()}. The calculated median is encoded in the 32-bit pulse value, while the pulse code identifies the job. The client can therefore receive the completion notification without requiring the server to reopen the original request.

\subsection{Phase 3: Retrieval and Post-Processing}

The client waits for the completion pulse using \texttt{MsgReceive()}. When the pulse arrives, it extracts the median and sends a separate fetch request using \texttt{MsgSend()} to obtain the result descriptor. This descriptor provides the offsets of the sorted and filtered arrays in shared memory.

Since the client has already mapped the shared memory region as read-only, it can access the arrays directly using these offsets. It also recalculates their FNV-1a checksums to verify that the retrieved data matches the expected results.

After all blocks have been processed, the client completes the remaining post-processing steps. These include calculating the global median, applying the required final filtering across the recording, and writing the output files: \texttt{raw.bin}, \texttt{sorted.bin}, \texttt{filtered.bin}, and \texttt{medians.csv}.

\section{Testing}
\label{sec:testing}

Every stage of this service has a plausible-looking failure mode. A sort that
loses one value, a filter that replaces a legitimate edge, a checksum computed
over the wrong bytes, a shared region read at the wrong offset: each still
produces numbers of the right shape, and inspection of the output alone would not
settle any of them. The tests are therefore built to compare against an answer
computed some other way, and to make the system prove that it refuses what it
should refuse.

Three words are used throughout, so they are worth defining. A \emph{check} is one
assertion: this value equals that one, this call returns $-1$. A \emph{test} is
a named group of checks exercising one behaviour, and a \emph{suite} is one binary
that runs a group of tests and prints a verdict. The counting is per check because
a test that quietly covers half of its cases still passes. ``0 skipped'' means
every check that could run did run: the payload tests are skipped when the
generated dataset is absent, so a run quoting zero skipped was made against the
real recording.

\subsection{Two folds, one set of sources}

The tests run twice, on two very different machines, from exactly the same source
files.

The \emph{host} fold is a set of plain C programs built with \texttt{gcc}. There is
no test framework: each file in \texttt{RT-MOMS/tests/} includes
\texttt{test\_util.h}, calls check macros and returns its own exit status, and
\texttt{make check} builds and runs the six suites in order. It is fast, it can be
instrumented, and it can do the two things the target cannot do comfortably:
compare against the C library's \texttt{qsort}, and feed malformed input on
purpose.

The \emph{board} fold cross-compiles the same sources with
\texttt{qcc -Vgcc\_ntoaarch64le} and runs them from the boot image on the
Raspberry Pi 4, where the compiler, the C library and the CPU are all different.
The board returns the same counts for the same suites, which is the point: with
the code held constant, the only thing left that could differ is the kernel, and
that is what the message passing, the pulse and the shared results region
exercise. The board run is therefore a confirmation of the host run rather than a
separate experiment; a disagreement would point at the environment, and
agreement means the behaviour is not an accident of one toolchain.

\chapter{Results and Discussions}

\section{Experimental Setup}

The experiments were conducted on a Raspberry Pi 4 running QNX Neutrino
RTOS. The target system was used to evaluate the complete client-server
pipeline, including block transfer, parallel merge-sort, rolling Hampel
filtering, shared-memory result retrieval and completion notification.

The input was a recorded battery sensor dataset,
\texttt{Chen2020\_c1\_T25\_discharge.bin}, replayed through the virtual
sensor interface. The recording contains 60,000 samples per selected
channel, stored as single-precision floating-point values. The configured
nominal sensor rate was 100 Hz, and the recording used the interleaved
layout containing time, voltage, current and temperature.

The client assembled blocks of 16,384 samples, corresponding to 64 KiB
per full block. A complete 60,000-sample recording was processed in
four blocks, with the last block containing the remaining 10,848 samples.

The server used a four-worker merge-sort pool for the window-width
experiments. The filter-width sweep covered widths of 3, 5, 7, 9, 11,
13, 15, 21 and 31 samples, with three repetitions per channel and width.
A separate worker-count sweep evaluated one, two, three and four workers
at the default filter width of 9.

The evaluation included functional correctness, filter quality, processing
time, repeated-run consistency and shared-memory bounds. Since the input
was replayed from a recording, the experiments validate execution on the
QNX hardware target but do not represent measurements from a physical
sensor connected directly to the board.

\section{Filter Quality and Outlier Removal (Width Sweep)}

\subsection{Overall Filter Quality}

The effect of filter width was evaluated on the Raspberry Pi 4 running
QNX Neutrino RTOS. The experiments used the recorded battery sensor
dataset and tested window widths of 3, 5, 7, 9, 11, 13, 15, 21 and
31 samples. Each configuration was executed three times.

Filter quality was evaluated for the voltage, current and temperature
channels using outlier-detection recall, the rate of replacing samples
not marked as outliers, and the change in reconstruction error after
filtering. These metrics assess both the ability to suppress abnormal
readings and the risk of altering valid measurements.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.88\textwidth]
    {run-figures/perf-width/width_quality.png}
    \caption{Filter quality metrics for different rolling-window widths.}
    \label{fig:width-quality}
\end{figure}

The width sweep illustrates the trade-off between outlier detection
and preservation of clean samples. A wider window provides a larger
neighbourhood for estimating the local median and MAD. However,
increasing the window width also increases computational cost and
may affect legitimate short-duration signal variations.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.92\textwidth]
    {run-figures/error_map.png}
    \caption{Error map comparing the raw and filtered sensor data
    against the reference signal.}
    \label{fig:filter-error-map}
\end{figure}

The error map complements the quality metrics by showing the
distribution of errors across the evaluated data. The quality and
error plots should be interpreted together, since reducing
reconstruction error does not necessarily mean that every injected
outlier has been detected or that every valid sample has been preserved.

The numerical results also demonstrate the effect of window width.
When the width increases from 9 to 15 samples, voltage outlier recall
increases from 73.77\% to 98.55\%, current recall increases from
63.57\% to 85.20\%, and temperature recall increases from 68.24\%
to 93.60\%. The corresponding RMSE decreases from 0.0039 to 0.0020
for voltage, from 0.0147 to 0.0085 for current, and from 0.1170 to
0.0638 for temperature.

These results indicate that a wider window performs better for the
injected outlier patterns in this dataset. However, the additional
processing cost must also be considered when selecting the operating
width. The default width of 9 is therefore a configuration choice
rather than a universally optimal setting.

\chapter{Conclusion and Scope for Further Research}

\section{Practical Industrial Applications}
\label{sec:applications}

The techniques used in this project, including parallel sorting, outlier filtering, and asynchronous IPC, are relevant to several embedded systems applications. The combination of these methods allows large data blocks to be processed efficiently while keeping communication overhead manageable. Some potential applications are discussed below.

\begin{itemize}
    \item \textbf{Battery Management Systems (BMS):} Battery monitoring systems collect voltage, current, and temperature measurements that may contain sudden spikes due to electrical switching or sensor noise. A rolling Hampel filter can help identify and remove these outliers, while sorting the measurements can support the analysis of cell voltage distributions and the identification of cells that may require further inspection.

    \item \textbf{Industrial Edge Gateways:} Industrial systems continuously collect data from vibration, temperature, and other sensors. Processing these measurements in fixed-size blocks using a worker-thread pool can improve throughput and reduce the processing burden on the main application thread. This helps separate data processing from time-sensitive monitoring and control tasks.

    \item \textbf{Automotive Sensor Processing (ADAS):} Advanced Driver Assistance Systems use measurements from sources such as radar, wheel-speed sensors, and other vehicle sensors. Filtering outliers and calculating statistics such as the median can help improve the quality of sensor data used by downstream processing. These operations may be implemented on real-time operating systems such as QNX, where predictable response times are important.

    \item \textbf{Flight and Railway Recorders:} These systems collect continuous streams of operational and sensor data for monitoring, analysis, and later investigation. Processing data in blocks, calculating checksums, and storing results in shared memory can support efficient data handling and integrity checks before the results are archived.
\end{itemize}

\section{Conclusion}
The project successfully implemented a real-time client-server architecture on QNX. The system demonstrated effective parallel sorting using POSIX threads and robust outlier removal using a Hampel filter. The use of QNX pulses and shared memory provided an efficient, low-latency method for data transfer and asynchronous notification.

\section{Scope for Further Research}
Future work could include:
\begin{itemize}
    \item Integrating a live hardware sensor (e.g., via I2C or SPI) instead of a virtual file-based sensor.
    \item Implementing dynamic thread allocation based on the current system load.
    \item Exploring alternative sorting algorithms (e.g., Radix Sort) for floating-point data.
    \item Adding a graphical user interface (GUI) for live monitoring of the metrics.
\end{itemize}
