\chapter{Introduction}

\section{Background and Motivation}

Embedded systems used for real-time data acquisition often need to process large amounts of sensor data while meeting strict timing requirements. Multi-core processors help meet these demands by allowing computational tasks to run in parallel. However, making effective use of multiple cores requires proper task distribution and synchronization, especially in systems where predictable execution time and responsiveness are important.

Sensor data may also contain unwanted variations, such as sudden spikes, bursts of abnormal readings, or dropouts caused by electromagnetic interference, sensor faults, or changes in operating conditions. Identifying and removing these outliers is important for obtaining reliable results during statistical analysis. Combining this filtering process with data sorting increases the computational workload. In a Real-Time Operating System (RTOS), these operations must be handled efficiently without affecting the system's ability to respond to inter-process communication (IPC) requests and hardware interrupts.

\section{Project Objectives}

This project focuses on developing a real-time client-server system using the QNX RTOS and deploying it on a Raspberry Pi 4. The system is designed to transfer unsorted floating-point time-series data from a client to a server in blocks of at least 64 KB for processing. The server performs two main operations:

\begin{enumerate}
    \item \textbf{Parallel Sorting:} A parallel Merge-Sort algorithm is implemented using multiple POSIX worker threads. Mutexes and condition variables are used to coordinate thread execution and synchronization during the sorting and merging stages.

    \item \textbf{Rolling Median Filtering:} A robust rolling median filter (Hampel filter) is applied to identify and remove outliers from the time-series data. The filter uses local median and median absolute deviation (MAD) values to detect abnormal readings while preserving the underlying signal.
\end{enumerate}

After processing, the server notifies the client through a QNX pulse event containing the calculated median and a descriptor specifying the relevant memory offset. The processed arrays remain in shared memory, allowing the client to access the results without requiring another complete data transfer.

\section{Workload and Dataset}

The system is evaluated using a synthetic dataset generated offline with PyBaMM, a Python-based battery modelling package. The dataset contains battery measurements, including current, voltage, and temperature, representing a simulated discharge cycle. To evaluate the ability of the filtering algorithm to detect abnormal readings, controlled noise and outliers are introduced into the data.

The dataset includes the following types of corruption:

\begin{itemize}
    \item \textbf{Gaussian Noise:} Additive white Gaussian noise is introduced into the measurements to simulate variations in sensor readings. Example noise levels include 2 mV for voltage and 8 mA for current.

    \item \textbf{Impulsive Outliers:} Outliers are introduced in the form of sudden spikes, consecutive bursts, and stuck readings. These outliers are introduced at random and occur at a rate of 1.5\%. A ground-truth mask is also maintained to identify the injected outliers and evaluate the filtering performance.
\end{itemize}

This dataset provides a controlled environment for evaluating the sorting and filtering algorithms under different data conditions. It also allows the results to be compared against the known locations of the injected outliers.

\section{Introduction}

\section{System Architecture and Block Diagram}
The system is based on a client-server model running on QNX. The client reads data from a virtual sensor and offloads it in 64 KB blocks to the server. The server utilizes a multi-threaded approach to sort the data and apply a Hampel filter. The results are written to a shared memory region.

\section{Client-Server Communication Sequence}
Communication between the two processes follows a strict sequence to ensure data integrity and asynchronous notification. 
\begin{enumerate}
    \item The client connects to the server using \texttt{name\_open}.
    \item The client sends a 64 KB block using an IOV message (\texttt{MsgSendv}).
    \item The server validates the block, sends an acknowledgement, and queues the job.
    \item Once processing is complete, the server sends a QNX pulse back to the client.
    \item The client retrieves the result descriptor using a fetch message.
\end{enumerate}

\section{Introduction}
This chapter details the implementation of the core algorithms, the data structures, and the QNX-specific mechanisms used to build the service.

\section{Virtual Sensor}
\label{sec:sensor}

There is no physical sensor on the bench, so the service is fed by a module that
replays a recording with the behaviour of a live device. Values arrive one sample
at a time, in frames, on a clock the module keeps itself rather than at the speed
of the host. The purpose is not convenience: with the sensor behind this
interface the client and the rest of the pipeline can be developed and tested
exactly as they will run against hardware, and a real device can replace the
module later without changing anything downstream.

\subsection{Addressing a sample in either layout}

Both layouts are headerless little-endian \texttt{float32}, and both are read by
one expression, where \texttt{next} is the sample the sensor is about to deliver:

\begin{equation}
  \texttt{value} = \texttt{window}\bigl[(\texttt{next} - \texttt{window\_first})
  \times \texttt{stride} + \texttt{offset}\bigr]
  \label{eq:sensor-address}
\end{equation}

A planar file is \texttt{stride} 1 and \texttt{offset} 0, so sample $i$ is float
$i$. An interleaved file is four floats per record --- time, voltage, current,
temperature --- so sample $i$ of the voltage channel is float $4i + 1$: record 1
is float 5, byte 20 of the file. The three unused floats of each record are read
from disk and discarded; a channel other than the selected one is never returned.
Figure~\ref{fig:sensor-layout} shows both cases.

\subsection{The read-ahead window}

The recording is not loaded whole. Reads pass through a sliding window of
\texttt{window\_samples} records --- 4096 by default, widened when the caller's
frame is larger --- which is refilled as the reader advances. In the real pipeline
the block loader asks for block-sized frames, so the window becomes 16\,384
records: 64\,KiB of a planar file or 256\,KiB of an interleaved one, in one call
to \texttt{fread}. A caller reading one sample at a time therefore sees exactly
the same values as a caller reading whole blocks, a property the tests use as an
independent check.

The refill condition is the three-part test in Listing~\ref{lst:sensor-read}: the
window is empty, the reader was rewound behind it, or it has walked past the end.
The loop applies the test before every sample, so no case can read stale data.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[caption={The read loop of \texttt{sensor\_read()}, trimmed of
its error returns. A device read delivers at most one frame; aggregating frames
into a block is the caller's job.}, label={lst:sensor-read},
basicstyle=\ttfamily\footnotesize]
while (n < cap) {
    if (s->next >= s->total) {
        if (!s->cfg.loop)
            break;                      /* end of the recording */
        s->next = 0;                    /* a live sensor never stops */
    }

    if (s->window_count == 0 ||         /* nothing read yet */
        s->next < s->window_first ||    /* rewound behind the window */
        s->next >= s->window_first + s->window_count)
        sensor_fill(s, s->next);        /* refill at the new position */

    offset = (s->next - s->window_first) * s->cfg.stride + s->cfg.offset;
    dst[n++] = s->window[offset];       /* the one channel that was asked for */
    s->next++;
    s->delivered++;
}
\end{lstlisting}
\end{minipage}

\subsection{Frames, blocks and the sensor's clock}

A device read returns a frame, not an arbitrary amount of data:
\texttt{sensor\_read} delivers at most \texttt{frame\_samples} samples, and
\texttt{sensor\_read\_frame} delivers exactly one frame except at the end of a
recording. Assembling a 64\,KiB payload is the client's concern, which is what
\texttt{sensor\_read\_block} does: it calls \texttt{sensor\_read} until the block
is full, so the aggregation sits on the client side of the boundary rather than
inside the device.

The clock is arithmetic rather than a system timer. The timestamp of the next
sample is \texttt{sensor\_index} $\times 10^9 / \texttt{rate\_hz}$ nanoseconds,
computed from a counter of samples delivered, so after 600 samples at 100\,Hz it
is exactly 6\,s however fast the host runs; in loop mode the counter keeps
advancing across the wrap, as a sensor that never stops would.
\texttt{sensor\_read\_paced} adds a wait after each read so the stream holds the
configured rate. That wait and the monotonic clock behind it are the only
platform-specific code in the project --- \texttt{clock\_gettime} and
\texttt{nanosleep} on QNX, with one shim for the host build --- and its resolution
is a millisecond, so pacing is meaningful up to roughly 500\,Hz.

\subsection{Rejecting bad input, and the interface}

Nothing is assumed about the file. A missing path, an empty file, a length that is
not a whole number of \texttt{float32} values or of records, an offset outside the
record, a stride below one, an unknown layout, a frame or rate out of range ---
each returns a null handle or an error code and prints a sentence naming the
problem instead of reading nonsense. Reads follow the same discipline: the number
of samples delivered, 0 at the end of a recording, $-1$ for an error.

\section{Block Loader}
The block loader (\texttt{block\_loader.c}) aggregates these samples into exact 64 KB blocks (\texttt{PROTO\_BLOCK\_SAMPLES} of 16384 float32 values).

\section{Parallel Merge-Sort}
The server sorts each block using a parallel Merge-Sort algorithm. The sort is partitioned across multiple POSIX worker threads. A mutex and two condition variables (\texttt{work\_ready}, \texttt{phase\_done}) are used to synchronize the phases, ensuring that merge operations only begin after all preceding partition tasks are complete.

\section{Rolling Median Filter (Hampel Filter)}
To remove outliers, the server applies a Hampel-style rolling median filter. The filter calculates the median and Median Absolute Deviation (MAD) of a sliding window. If a sample deviates from the median by more than a configurable threshold (4.0 sigma), it is replaced. This preserves legitimate signal edges while removing sudden spikes.

\section{QNX IPC Mechanisms}
\subsection{Message Passing and IOV}
Large data blocks are transferred using \texttt{MsgSendv} (Input/Output Vectors) to avoid copying the 64 KB buffer into a single contiguous message.

\subsection{QNX Pulses and Asynchronous Notification}
Upon completion, the server sends a pulse. Because a pulse value is limited to 32 bits, the float representation of the calculated median is bit-cast directly into the pulse payload. The pulse code carries the Job ID.

\subsection{Shared Memory}
To avoid sending the large processed arrays back over IPC, the server maps a named shared memory region (\texttt{/dev/shmem/sortmed-results}). The server writes the sorted and filtered arrays directly into this region, and the client maps it read-only to retrieve the results.

\chapter{Conclusion and Scope for Further Research}

\section{Conclusion}
The project successfully implemented a real-time client-server architecture on QNX. The system demonstrated effective parallel sorting using POSIX threads and robust outlier removal using a Hampel filter. The use of QNX pulses and shared memory provided an efficient, low-latency method for data transfer and asynchronous notification.

\section{Scope for Further Research}
Future work could include:
\begin{itemize}
    \item Integrating a live hardware sensor (e.g., via I2C or SPI) instead of a virtual file-based sensor.
    \item Implementing dynamic thread allocation based on the current system load.
    \item Exploring alternative sorting algorithms (e.g., Radix Sort) for floating-point data.
    \item Adding a graphical user interface (GUI) for live monitoring of the metrics.
\end{itemize}
