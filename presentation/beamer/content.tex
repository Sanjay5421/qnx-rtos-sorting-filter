\section{Introduction}
% ===========================================================================

\begin{frame}{What the Service Does in One Breath}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.53\textwidth}
      \smalltext\compactitem
      A \concept{client} reads a continuous stream of floating-point sensor numbers, packs them into \textbf{64 KiB crates} (16\,384 numbers each), and hands each crate to a \concept{server} over QNX message passing.
      \vskip1mm
      For every crate, the server does two jobs:
      \begin{itemize}
        \item \textbf{Parallel Merge Sort}: Sorts a copy of the 16\,384 numbers across worker threads to find the exact block median and range.
        \item \textbf{Rolling Median Filter}: Slides a small odd-width window across the time-ordered numbers to strip out one-off sensor spikes.
      \end{itemize}
      \vskip1mm
      When done, the server sends a \concept{QNX pulse} so the client never has to sit waiting.
    \end{column}
    \begin{column}{0.44\textwidth}
      \smalltext\compactitem
      \begin{highlight}
        \textbf{Quick Vocabulary}
        \begin{itemize}
          \item \textbf{Sample}: One \texttt{float} reading (4 B), e.g.\ \texttt{3.71 V}.
          \item \textbf{Record}: One moment holding all 4 channels (16 B).
          \item \textbf{Frame}: 128 samples returned per sensor read.
          \item \textbf{Block}: 16\,384 samples = 64 KiB sent at once.
        \end{itemize}
      \end{highlight}
      \vskip0.5mm
      \begin{tech}
        \textbf{Course Rules Met} \\
        QNX synchronous \texttt{MsgSendv}, $\ge$\,64 KiB payload per transfer, multi-threaded sort, and async pulse notification.
      \end{tech}
    \end{column}
  \end{columns}
\end{frame}

% ---------------------------------------------------------------------------
\begin{frame}{Why a Median Filter Instead of an Average?}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.50\textwidth}
      Suppose a battery sensor sits at 5.0 V, and one loose-wire glitch makes a single reading jump to 50.0 V:
      \vskip1mm
      \begin{center}
      \fitwidth{%
      \begin{tabular}{@{}lccc@{}}
        \toprule
        \rtmtablehead{5 Readings in Window} & \rtmtablehead{Average} & \rtmtablehead{Median} & \rtmtablehead{Real Value} \\
        \midrule
        5.0, 5.0, 5.0, 5.0, 5.0   & 5.0 V  & 5.0 V & 5.0 V \\
        5.0, 5.0, 5.0, 5.0, 50.0  & \num{14.0 V} & \num{5.0 V} & 5.0 V \\
        \bottomrule
      \end{tabular}}
      \end{center}
      \vskip1mm
      A moving average gets pulled from 5 V up to \textbf{14 V} by one bad reading. The \textbf{median} sorts the 5 numbers and picks the middle one — still \textbf{5.0 V}.
    \end{column}
    \begin{column}{0.47\textwidth}
      \smalltext\compactitem
      \begin{itemize}
        \item \textbf{Why an odd window width?} With 3, 5, or 7 samples, there is always one exact middle sample after sorting the window.
        \item \textbf{Why keep a separate copy?} Sorting the whole 16\,384-sample block destroys time order. The rolling median filter must run on the original time-ordered sequence.
        \item \textbf{Why do both?} Full-block sort gives overall percentiles (min, median, max); the rolling filter gives a clean, spike-free waveform.
      \end{itemize}
    \end{column}
  \end{columns}
\end{frame}

\begin{frame}{How the Virtual Sensor Works (\texttt{app/sensor.c})}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.52\textwidth}
      \smalltext\compactitem
      \texttt{sensor.c} wraps the binary recording on disk and makes it behave like live hardware:
      \begin{itemize}
        \item \textbf{Checks file on open}: Verifies byte size is a multiple of $4\text{ floats} \times 4\text{ B} = 16\text{ B}$. Rejects bad rates, zero strides, or invalid offsets right away.
        \item \textbf{4096-record sliding window}: Keeps only 4096 records in RAM and refills via \texttt{fread()} when the cursor walks past the window.
        \item \textbf{128-sample frames}: Like a hardware ADC FIFO, \texttt{sensor\_read()} returns at most 128 samples per call.
        \item \textbf{Paced or unpaced}: \texttt{sensor\_read\_paced()} sleeps against \texttt{CLOCK\_MONOTONIC} to match real-time Hz; unpaced reads run at full CPU speed.
      \end{itemize}
    \end{column}
    \begin{column}{0.45\textwidth}
      \smalltext\compactitem
      \begin{highlight}
        \textbf{Picking Voltage from 4 Channels} \\
        Each record stores \texttt{[Time, Voltage, Current, Temp]}. To read only Voltage, we open with \textbf{\texttt{stride = 4, offset = 1}}: step by 4 floats, always pick slot 1.
      \end{highlight}
      \vskip0.5mm
      \begin{tech}
        \textbf{Drift-Free Sensor Timestamp} \\
        Computed directly from the sample counter:
        $t_{\text{ns}} = (\text{delivered} \times 10^9) / \text{rate\_hz}$.
        At 100 Hz, sample 100 is always $1.000\text{ s}$, unaffected by OS sleep jitter.
      \end{tech}
    \end{column}
  \end{columns}
\end{frame}

\begin{frame}{How the Block Loader Works (\texttt{app/block\_loader.c})}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.51\textwidth}
      \smalltext\compactitem
      The sensor hands out small 128-sample frames, while the server expects full \textbf{16\,384-sample (64 KiB) blocks}. \texttt{block\_loader.c} bridges the two:
      \begin{itemize}
        \item \textbf{Single place for channel offsets}: \texttt{block\_loader\_channel\_offset()} maps channel names to their slot in the 4-float record:
        \vskip0.5mm
        {\scriptsize \texttt{VOLTAGE $\rightarrow$ 1,\quad CURRENT $\rightarrow$ 2,\quad TEMP $\rightarrow$ 3}}
        \item \textbf{Gathers frames into a crate}: Loops over \texttt{sensor\_read()} until 16\,384 samples are collected (128 frames) or the file ends.
        \item \textbf{Fills out the shipping label}: Scans the collected samples for \texttt{min\_val} and \texttt{max\_val}, sets \texttt{seq}, and stamps the FNV-1a checksum.
      \end{itemize}
    \end{column}
    \begin{column}{0.46\textwidth}
      \smalltext\compactitem
      \begin{highlight}
        \textbf{What happens on the 4th block?} \\
        60\,000 samples $= 3 \times 16\,384 + \mathbf{10\,848}$. \\
        The 4th block has 10\,848 real readings. The loader zeroes the remaining \textbf{5\,536 slots} so leftover RAM garbage never crosses processes.
      \end{highlight}
      \vskip0.5mm
      \begin{tech}
        \textbf{Why checksum only \texttt{desc->samples}?} \\
        The seal hashes only the \textbf{10\,848 real samples}, not the 5\,536 padding zeros, so the server sorts and medians only real battery readings.
      \end{tech}
    \end{column}
  \end{columns}
\end{frame}

\begin{frame}{Protocol Conversation Between Client \& Server}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.52\textwidth}
      \texttt{app/protocol.h} defines the 5 messages used across QNX IPC:
      \vskip1mm
      \begin{center}
      \fitwidth{%
      \begin{tabular}{@{}lll@{}}
        \toprule
        \rtmtablehead{Step / Message} & \rtmtablehead{Size} & \rtmtablehead{What Happens} \\
        \midrule
        1. \texttt{SUBMIT + BLOCK} & 48 B + 64 KiB & Client sends label + crate (2-part IOV) \\
        2. \texttt{ACK}            & 8 B           & Server checks seal, replies right away \\
        3. \texttt{PULSE} (code 16)& 1 B code      & Server taps client when sort finishes \\
        4. \texttt{FETCH}          & 8 B           & Client asks for finished job's numbers \\
        5. \texttt{RESULT}         & 48 B          & Server returns median, min/max, offsets \\
        \bottomrule
      \end{tabular}}
      \end{center}
    \end{column}
    \begin{column}{0.45\textwidth}
      \smalltext\compactitem
      \begin{highlight}
        \textbf{Why reply with \texttt{ACK} before sorting?} \\
        In QNX, \texttt{MsgSendv} blocks the client until the server calls \texttt{MsgReply}. Replying with \texttt{ACK} immediately lets the client keep reading the sensor while workers sort.
      \end{highlight}
      \vskip0.5mm
      \begin{tech}
        \textbf{Compile-Time Safety Guards} \\
        \texttt{STATIC\_ASSERT} pins \texttt{sizeof(proto\_block\_t)} to 65\,536 B. Message IDs start at \texttt{0x1000}, well above QNX system messages (\texttt{0x000}--\texttt{0x1FF}).
      \end{tech}
    \end{column}
  \end{columns}
\end{frame}

\begin{frame}{Protocol Definition: Shared Results Region}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.54\textwidth}
      The pulse only says \emph{a job is done}; the arrays are handed over in a
      \concept{named shared region}, defined in the same header:
      \vskip1mm
      \fitwidth{%
      \begin{tabular}{@{}lll@{}}
        \toprule
        \rtmtablehead{Part} & \rtmtablehead{Size} & \rtmtablehead{Contents} \\
        \midrule
        region header & 24 B & magic, version, slot count \\
        slot header   & 16 B & job id, state word \\
        sorted[]      & 64 KiB & the sorted block \\
        filtered[]    & 64 KiB & the time-ordered copy \\
        \bottomrule
      \end{tabular}}
      \vskip1.5mm
      {\footnotesize Region \texttt{/sortmed-results}: one header plus
       \num{4} slots, so four results can be in flight.}
    \end{column}
    \begin{column}{0.43\textwidth}
      \begin{tech}
        \textbf{A state word, not a lock} \\
        The server publishes a slot by writing \texttt{WR2D} to its state word.
        A slot still reading \texttt{FREE} has not been written. The client
        re-reads that one word — no mutex is shared across the programs.
      \end{tech}
      \vskip1.5mm
      \begin{highlight}
        \textbf{The result points, it does not carry} \\
        \texttt{proto\_result\_t} holds \texttt{sorted\_offset},
        \texttt{filtered\_offset}, \texttt{length}, and two checksums, all
        32-bit. Offset 0 means ``not produced''.
      \end{highlight}
      \vskip1mm
      {\footnotesize Three tests pin the region: its name, its layout, and
       that the result describes it.}
    \end{column}
  \end{columns}
\end{frame}

\begin{frame}{How Parallel Merge Sort Splits \& Merges (\texttt{mergesort.c})}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.53\textwidth}
      \smalltext\compactitem
      How a 16\,384-sample crate is sorted across \textbf{4 worker threads}:
      \begin{itemize}
        \item \textbf{How many slices?}: $k = \min(n / 1024,\, \text{threads})$ $\rightarrow$ \textbf{4 slices} of \textbf{4\,096 samples} each. (Blocks $<4096$ run on 1 thread.)
        \item \textbf{Phase 0 — Sort 4 slices (4 tasks)}: All 4 workers run in parallel, sorting their 4\,096-sample slice into scratch.
        \item \textbf{Phase 1 — First merge (2 tasks)}: Two workers merge pairs of 4\,096 into two runs of \textbf{8\,192} in the main buffer.
        \item \textbf{Phase 2 — Final merge (1 task)}: One worker merges the two 8\,192 runs into the final \textbf{16\,384} sorted array.
      \end{itemize}
      {\scriptsize Total plan: \textbf{4 partitions, 2 merge phases, 7 tasks ($4 + 2 + 1$)}.}
    \end{column}
    \begin{column}{0.44\textwidth}
      \smalltext\compactitem
      \begin{highlight}
        \textbf{Ping-Pong Scratch Buffer} \\
        One 64 KiB scratch buffer is allocated when the pool starts. Phases bounce between \texttt{buf\_a} and \texttt{buf\_b} with zero per-job \texttt{malloc}.
      \end{highlight}
      \vskip0.5mm
      \begin{tech}
        \textbf{Thread-Invariant Output} \\
        When merging two halves, ties always pick from the left half (\texttt{a[i] <= b[j]}). Output is \textbf{bit-for-bit identical} across 1, 2, 4, and 8 threads.
      \end{tech}
    \end{column}
  \end{columns}
\end{frame}

\begin{frame}[fragile]{Parallel Merge Sort: Line-by-Line Code Walkthrough}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.53\textwidth}
\begin{lstlisting}
/* 1. Manager posts a phase & waits (mergesort.c) */
static void post_phase(mergesort_pool_t *p, unsigned ntasks) {
    pthread_mutex_lock(&p->lock);
    p->ntasks = ntasks; p->next_task = 0; p->tasks_done = 0;
    pthread_cond_broadcast(&p->work_ready);
    while (p->tasks_done < p->ntasks)
        pthread_cond_wait(&p->phase_done, &p->lock);
    pthread_mutex_unlock(&p->lock);
}
/* 2. Inside each worker thread loop */
unsigned idx = p->next_task++;
mergesort_task_t t = p->tasks[idx];
pthread_mutex_unlock(&p->lock);
run_task(&t); /* sorts/merges unlocked in parallel */
pthread_mutex_lock(&p->lock);
if (++p->tasks_done == p->ntasks)
    pthread_cond_signal(&p->phase_done);
\end{lstlisting}
    \end{column}
    \begin{column}{0.44\textwidth}
      \smalltext\compactitem
      \begin{itemize}
        \item \textbf{Lines 3--5 (Publish phase)}: Locks mutex, sets \texttt{ntasks} (4, then 2, then 1), resets counters, and broadcasts \texttt{work\_ready}.
        \item \textbf{Lines 6--7 (Phase barrier)}: Manager sleeps on \texttt{phase\_done} until all tasks in this phase finish.
        \item \textbf{Lines 11--14 (Parallel work)}: Worker claims ticket \texttt{next\_task++}, \textbf{unlocks mutex immediately}, and runs \texttt{run\_task()} on its core.
        \item \textbf{Lines 15--17 (Wake manager)}: Last finisher (\texttt{tasks\_done == ntasks}) signals \texttt{phase\_done} to advance phases.
      \end{itemize}
    \end{column}
  \end{columns}
\end{frame}

\begin{frame}{How the Rolling Median Filter Works (\texttt{app/median.c})}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.52\textwidth}
      \smalltext\compactitem
      \texttt{median.c} computes both the sorted-array median and a \textbf{Hampel rolling median filter} on the time-ordered signal:
      \begin{itemize}
        \item \textbf{Centered odd window}: Slides an odd window (default \texttt{width = 9}, range $3..31$) across the original samples.
        \item \textbf{Window median \& MAD}: Orders the small window on the stack via insertion sort to get the local \texttt{median} and the median absolute deviation (\texttt{mad}).
        \item \textbf{Replaces only true spikes}: Converts MAD to robust sigma ($\sigma = 1.4826 \times \text{MAD}$). Replaces a sample \textbf{only} if it exceeds $4\sigma$ from the window median; clean samples pass through untouched.
      \end{itemize}
    \end{column}
    \begin{column}{0.45\textwidth}
      \smalltext\compactitem
      \begin{highlight}
        \textbf{Why Hampel Instead of Plain Median?} \\
        A plain median replaces every point and rounds off clean voltage ramps. Hampel replaces only the $10$--$40\sigma$ spikes and leaves clean readings bit-exact.
      \end{highlight}
      \vskip0.5mm
      \begin{tech}
        \textbf{Seamless Block Boundaries} \\
        Accepts up to \texttt{(width-1)/2} neighbour samples (\texttt{left}, \texttt{right}) so block seams produce the exact same output as filtering the whole recording at once.
      \end{tech}
    \end{column}
  \end{columns}
\end{frame}

\begin{frame}[fragile]{Rolling Median Filter: Line-by-Line Code Walkthrough}

/* Inside median_filter_block() in app/median.c */
for (k = 0; k < count; k++)
    window[k] = sample_at(lo + (ptrdiff_t)k, left,
                          (ptrdiff_t)nleft, cur, (ptrdiff_t)n, right);
sort_small(window, count);
median = middle_of(window, count);

for (k = 0; k < count; k++)
    deviation[k] = fabsf(window[k] - median);
sort_small(deviation, count);
mad = middle_of(deviation, count);

if (fabsf(centre - median) >
    cfg->threshold * MEDIAN_MAD_TO_SIGMA * mad) {
    out[i] = median;
    replaced++;
} else {
    out[i] = centre;
}

        \item \textbf{Lines 8--11 (Compute MAD)}: Measures each neighbor's distance \texttt{|x - median|}, sorts those distances, and takes their middle value (\texttt{mad}).
        \item \textbf{Lines 13--18 (Spike test)}: If \texttt{centre} is further than \texttt{4.0 * 1.4826 * mad}, replaces it with \texttt{median} and bumps \texttt{replaced}; otherwise keeps \texttt{centre}.
      \end{itemize}

\begin{frame}{How the QNX Server \& Client Work (\texttt{server.c}, \texttt{client.c})}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.51\textwidth}
      \smalltext\compactitem
      \textbf{Server (\texttt{sortmed-server}):}
      \begin{itemize}
        \item Creates \texttt{/sortmed-results} shared memory (\texttt{shm\_region\_create}) and attaches channel \texttt{"sortmed"}.
        \item Receives \texttt{\{submit, block\}} via \texttt{MsgReceivev}, verifies checksum, and replies \texttt{ACK} immediately.
        \item Sorts one copy in shared memory via \texttt{ms\_sort()}, filters a second copy via \texttt{median\_filter\_block()}, marks slot \texttt{WR2D}, and sends pulse code 16.
      \end{itemize}
    \end{column}
    \begin{column}{0.46\textwidth}
      \smalltext\compactitem
      \textbf{Client (\texttt{sortmed-client}):}
      \begin{itemize}
        \item Attaches \texttt{"sortmed-client"} for pulses and maps \texttt{/sortmed-results} read-only.
        \item Sends each 64 KiB block with \texttt{MsgSendv}, waits for the completion pulse, and sends \texttt{FETCH}.
        \item Verifies slot state \texttt{WR2D}, bounds, and FNV-1a checksums, then writes \texttt{raw.bin}, \texttt{sorted.bin}, \texttt{filtered.bin}, and \texttt{medians.csv}.
      \end{itemize}
    \end{column}
  \end{columns}
\end{frame}

\begin{frame}{One-Time Clarification: Planar vs Interleaved Files}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.48\textwidth}
      \smalltext\compactitem
      \begin{tech}
        \textbf{Planar File (Single-Channel Check)} \\
        One file per signal (\texttt{r1\_voltage.bin}). 60\,000 voltages in a row (240\,000 B): \\
        \texttt{[V0, V1, V2...]} (\texttt{stride=1, offset=0}).
      \end{tech}
      \vskip1mm
      \begin{tech}
        \textbf{Interleaved File (Production Payload)} \\
        One unified file (\texttt{Chen2020\_c1...bin}). 60\,000 moments $\times$ 4 channels (960\,000 B): \\
        \texttt{[t0, V0, I0, T0, t1, V1, I1, T1...]} \\
        (\texttt{stride=4, offset=k}).
      \end{tech}
    \end{column}
    \begin{column}{0.49\textwidth}
      \smalltext\compactitem
      \begin{highlight}
        \textbf{Why This Distinction Matters in Code} \\
        If you sort an interleaved file directly without picking channel offset $k$, you sort \textbf{seconds against volts against amps against kelvin} — the numbers sort, but the result is meaningless!
      \end{highlight}
      \vskip1mm
      \begin{itemize}
        \item \texttt{block\_loader\_channel\_offset()} ensures we extract only one physical quantity (Voltage at \texttt{offset = 1}).
        \item Planar files were used \textbf{only once in tests} to verify that strided extraction produces the exact same 4 checksums.
        \item \concept{All production runs use the Interleaved file}.
      \end{itemize}
    \end{column}
  \end{columns}
\end{frame}
