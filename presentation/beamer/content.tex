% ===========================================================================
\section{Introduction}
% ===========================================================================

\begin{frame}{The problem}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.54\textwidth}
      A client continuously offloads \concept{unsorted floating-point
      time-series} metrics to a server. The server
      \begin{itemize}
        \item sorts each block with a \concept{parallel merge sort},
        \item removes sensor outliers with a \concept{rolling median},
        \item and \concept{signals completion asynchronously}.
      \end{itemize}
      \vskip2mm
      The client then collects the median and a memory-offset descriptor —
      the two things the service exists to produce.
    \end{column}
    \begin{column}{0.42\textwidth}
      \begin{highlight}
        \textbf{Why it is hard} \\
        The workload arrives faster than it can be handled one sample at a
        time, and the readings are corrupted by spikes that no average
        survives.
      \end{highlight}
      \vskip2mm
      \begin{tech}
        \textbf{The rules} \\
        Message passing only, a client--server split, a two-part IOV
        transfer, a payload of at least 64 KB, and an asynchronous event.
      \end{tech}
    \end{column}
  \end{columns}
\end{frame}

% ---------------------------------------------------------------------------
\begin{frame}{Why a median, and not an average}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.50\textwidth}
      A sensor reading is one number in a stream. An outlier is a reading
      that the sensor, or the wiring, invented.
      \vskip2mm
      \begin{center}
      \begin{tabular}{@{}lccc@{}}
        \toprule
        \rtmtablehead{Window} & \rtmtablehead{Mean} & \rtmtablehead{Median} & \rtmtablehead{Truth} \\
        \midrule
        5, 5, 5, 5, 5   & 5.0  & 5.0 & 5 \\
        5, 5, 5, 5, 50  & \num{14.0} & \num{5.0} & 5 \\
        \bottomrule
      \end{tabular}
      \end{center}
      \vskip2mm
      One spike moves the mean by 9 V and the median not at all. That is the
      entire argument.
    \end{column}
    \begin{column}{0.46\textwidth}
      \begin{itemize}
        \item The filter slides a window of neighbouring samples and takes
              the middle value.
        \item The window must be \concept{odd}, so a middle value exists.
        \item It needs the signal in \concept{time order} — so it cannot run
              on the buffer the sort has just reordered.
      \end{itemize}
      \vskip2mm
      \begin{highlight}
        On our payload the median removes the injected spikes outright;
        what remains is the bias it leaves on a step or a ramp, which no
        median can avoid.
      \end{highlight}
    \end{column}
  \end{columns}
\end{frame}

% ---------------------------------------------------------------------------
\begin{frame}{What we set out to build}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.50\textwidth}
      \begin{tech}
        \textbf{Agree on the message first} \\
        Both programs share one header file. It was written before any QNX
        code, so the client and the server could not drift apart — and it can
        be tested on a PC.
      \end{tech}
      \vskip2mm
      \begin{tech}
        \textbf{Build it in stages, test it off the board} \\
        Sensor, then loader, then sort — each finished and tested before the
        next starts. Almost none of the code needs QNX, so it runs on a PC
        first; the board is where we take the numbers, not where we debug.
      \end{tech}
    \end{column}
    \begin{column}{0.46\textwidth}
      \begin{itemize}
        \item \concept{One block, one job} — every block is exactly 64 KiB,
              so the size requirement needs no special case.
        \item \concept{Same answer every time} — the result must not change
              with the number of threads, so it can be checked.
        \item \concept{Show the receipts} — every number on a slide is a
              command run on the Raspberry Pi 4.
      \end{itemize}
    \end{column}
  \end{columns}
\end{frame}

\begin{frame}{The two programs}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.47\textwidth}
      \begin{highlight}
        \textbf{Client — the offload side}
      \end{highlight}
      \vskip1mm
      \begin{itemize}
        \item Connects by \concept{name only} (\texttt{name\_open}), retrying
              to a 10-second deadline rather than hanging.
        \item Replays a recording, assembles blocks, sends each as a two-part
              IOV.
        \item Owns its own connection, which is why the event can reach it
              later.
      \end{itemize}
    \end{column}
    \begin{column}{0.49\textwidth}
      \begin{highlight}
        \textbf{Server — the compute side}
      \end{highlight}
      \vskip1mm
      \begin{itemize}
        \item \texttt{name\_attach} registers the name; the receive loop
              never blocks on a sort.
        \item Validates the descriptor, verifies the checksum, replies with
              the ack, and only then queues the job.
        \item Raises the event with a pulse and answers the fetch with the
              median and the offset descriptor.
      \end{itemize}
    \end{column}
  \end{columns}
  \vskip2mm
  \key{The ack says "accepted"; the pulse says "done"; the fetch carries the answer}
\end{frame}

% ---------------------------------------------------------------------------
\begin{frame}{The message definition}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.50\textwidth}
      One header file, \texttt{protocol.h}, is compiled into both programs.
      The whole exchange is five messages:
      \vskip1mm
      \begin{center}
      \begin{tabular}{@{}ll@{}}
        \toprule
        \rtmtablehead{Message} & \rtmtablehead{What it does} \\
        \midrule
        \texttt{SUBMIT} & header + block, one send \\
        \texttt{ACK}    & accepted, or why not \\
        \texttt{PULSE}  & sent later, when the work is done \\
        \texttt{FETCH}  & client asks for the answer \\
        \texttt{RESULT} & the median and the offset descriptor \\
        \bottomrule
      \end{tabular}
      \end{center}
    \end{column}
    \begin{column}{0.46\textwidth}
      \begin{tech}
        \textbf{The block travels beside the descriptor} \\
        The server reads 48 bytes, decides, then pulls the 64 KiB. It never
        needs a 64 KiB buffer just to learn how big the message is.
      \end{tech}
      \vskip2mm
      \begin{highlight}
        \textbf{The checksum covers only the declared samples} \\
        A short final block's tail is never checksummed, so the value cannot
        depend on stale buffer contents.
      \end{highlight}
      \vskip2mm
      {\footnotesize The client chooses the \concept{job id} and the server
       echoes it in the ack, the pulse and the result, which is how a
       completion is matched to its request.}
    \end{column}
  \end{columns}
\end{frame}

% ---------------------------------------------------------------------------
\begin{frame}{Implementation: the virtual sensor}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.50\textwidth}
      \begin{itemize}
        \item The recording is a headerless file of float32 values, so its
              size is its only metadata: sample count is
              \texttt{bytes / 4}.
        \item Samples are read through a \concept{sliding window} of 4096,
              refilled as the reader advances — never the whole file at once.
        \item A read delivers at most \concept{one frame} (128 samples), as a
              device would. Gathering frames into a 64 KiB block is the
              client's job, not the sensor's.
        \item The timestamp is computed, not measured:
              \texttt{index / rate}, so it does not drift with the host.
      \end{itemize}
    \end{column}
    \begin{column}{0.46\textwidth}
      \begin{tech}
        \textbf{Nothing is assumed about the file} \\
        A missing file, an empty file, a size that is not a whole number of
        float32 values, a frame or rate out of range — each is refused by
        name, and the message says which one it was.
      \end{tech}
      \vskip2mm
      \begin{highlight}
        \texttt{test\_sensor} — \textbf{15 tests, 642 checks} \\
        Exact float round trips, frame capping, end of file, window refills
        at unaligned offsets, timestamps and paced reads.
      \end{highlight}
    \end{column}
  \end{columns}
\end{frame}

% ---------------------------------------------------------------------------
\begin{frame}{Implementation: the block loader}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.50\textwidth}
      \begin{itemize}
        \item Turns the sample stream into the unit the service moves:
              \concept{16\,384 samples = exactly 64 KiB}, one block per read
              of the sensor.
        \item Alongside each block it fills a \concept{descriptor}: sequence,
              first sample, count, rate, channel, min/max and the checksum.
        \item \concept{A short final block is zero-padded.} 60\,000 samples
              become three full blocks and one of 10\,848.
      \end{itemize}
    \end{column}
    \begin{column}{0.46\textwidth}
      \begin{highlight}
        Why padding matters \\
        The whole 64 KiB crosses to another program, and uninitialised bytes
        should never travel. Zeroing them also makes the block reproducible.
      \end{highlight}
      \vskip2mm
      \begin{tech}
        \textbf{\texttt{test\_block\_loader} — 8 tests, 116 checks} \\
        A synthetic 20\,000-sample file splitting as 16\,384 + 3616 and
        reassembling exactly, and a single changed sample being caught.
      \end{tech}
    \end{column}
  \end{columns}
\end{frame}

% ---------------------------------------------------------------------------
\begin{frame}[fragile]{Implementation: the parallel merge sort}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.50\textwidth}
      \begin{itemize}
        \item A pool of POSIX worker threads sorts one block at a time.
        \item \textbf{Phase 0}: each worker sorts one partition.
        \item \textbf{After that}: pairs of sorted runs are merged, halving
              the number until one run covers the block.
        \item The phase boundary is a \concept{real barrier} — one mutex and
              two condition variables. Nothing is ordered by a sleep.
        \item One scratch buffer is ping-ponged between phases: one
              allocation per block, none per merge.
      \end{itemize}
    \end{column}
    \begin{column}{0.46\textwidth}
\begin{lstlisting}
/* merge: take the smaller head */
while (i < n1 && j < n2)
    out[k++] = (a[i] <= b[j]) ? a[i++] : b[j++];
\end{lstlisting}
      \vskip1mm
      \begin{highlight}
        \texttt{test\_mergesort} — \textbf{13 tests, 578 checks} \\
        Every size from 0 to 64, the sizes around the 4096 threshold, the
        partition boundaries, all-equal and reverse-sorted input,
        $\pm$0.0 and the float extremes.
      \end{highlight}
    \end{column}
  \end{columns}
  \vskip1mm
  \key{Equal values keep their order, so 1 worker and 8 agree exactly}
\end{frame}

\begin{frame}{One recording on disk}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.48\textwidth}
      One channel is one file — a flat run of float32 values, no header:
      \vskip1mm
      \begin{center}
      \begin{tabular}{@{}ll@{}}
        \toprule
        \rtmtablehead{File} & \rtmtablehead{Contents} \\
        \midrule
        \texttt{r1\_voltage.bin} & 60\,000 samples, 240\,000 B \\
        \texttt{r1\_current.bin} & 60\,000 samples, 240\,000 B \\
        \bottomrule
      \end{tabular}
      \end{center}
      \vskip1mm
      \begin{itemize}
        \item A whole file is \concept{one signal}, so a minimum or maximum
              over it means something.
        \item The file length is the only metadata there is: 240\,000 bytes
              is exactly 60\,000 values.
      \end{itemize}
    \end{column}
    \begin{column}{0.48\textwidth}
      \begin{tech}
        \textbf{Reading a sample is arithmetic} \\
        Sample \texttt{i} sits at byte \texttt{i * 4}. The loader turns that
        into blocks by reading a continuous run — no seeking per sample.
      \end{tech}
      \vskip2mm
      \begin{highlight}
        \textbf{The channel is carried, not assumed} \\
        The blocks are labelled with which signal they hold, so a block of
        voltage can never be presented as current downstream.
      \end{highlight}
    \end{column}
  \end{columns}
\end{frame}

% ---------------------------------------------------------------------------
\begin{frame}{Sorting a block with four workers}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.47\textwidth}
      \begin{itemize}
        \item \textbf{Phase 0} — each worker sorts one partition into the
              scratch buffer.
        \item \textbf{Merge phases} — pairs of runs are merged until one run
              covers the array.
        \item A merge reads two runs the previous phase produced, so the
              phase boundary is a \concept{real barrier}: one mutex, a
              work-ready and a phase-done condition variable.
        \item Nothing is ordered by a sleep, so a slow machine cannot
              produce a different answer.
      \end{itemize}
    \end{column}
    \begin{column}{0.49\textwidth}
      \begin{tech}
        \textbf{Deterministic by construction} \\
        The merge takes from the left run on ties, so equal values keep
        their order and the output is bit-identical for 1, 2, 3, 5 and 8
        threads.
      \end{tech}
      \vskip2mm
      \begin{tech}
        \textbf{One allocation per sort} \\
        A single scratch buffer is ping-ponged between phases. Inputs below
        4096 values take the serial path, where a pool costs more than it
        saves.
      \end{tech}
      \vskip2mm
      \key{4 partitions \textbullet{} 2 merge phases \textbullet{} 7 tasks}
    \end{column}
  \end{columns}
\end{frame}

\section{Methodology}
% ===========================================================================

\begin{frame}{How it was built}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.47\textwidth}
      {\color{rtmMuted}\ttfamily\scriptsize\bfseries THE ORDER OF WORK}\par
      \vskip2mm
      \begin{enumerate}
        \item \concept{Protocol} — the interface both sides compile
              against, proved on the host before any kernel code.
        \item \concept{Sensor} — replay a recording like a device, in
              frames, on its own clock.
        \item \concept{Block loader} — turn the stream into 64 KiB blocks
              with descriptors.
        \item \concept{Merge sort} — the parallel phase machinery, measured
              against \texttt{qsort}.
        \item \concept{Image} — cross-compile, pack, boot, run.
      \end{enumerate}
    \end{column}
    \begin{column}{0.49\textwidth}
      \begin{tech}
        \textbf{Five programs, one library} \\
        \texttt{sensor.c}, \texttt{protocol.c}, \texttt{block\_loader.c} and
        \texttt{mergesort.c} are linked into every binary — the tests and
        the demos exercise the same code the service will run.
      \end{tech}
      \vskip2mm
      \begin{tech}
        \textbf{Host build, target build, one source} \\
        \texttt{-std=c99 -Wall -Wextra -pedantic} clean on both. The only
        platform-dependent file is the sensor's clock and sleep, behind one
        \texttt{\#if defined(\_WIN32)}.
      \end{tech}
    \end{column}
  \end{columns}
\end{frame}

\begin{frame}{From source to a booting board}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.50\textwidth}
      \begin{enumerate}
        \item \texttt{app/Makefile} cross-compiles every program for
              \texttt{aarch64le} with
              \texttt{qcc -Vgcc\_ntoaarch64le}.
        \item \texttt{make install} places the binaries and the payload in
              the BSP's install tree.
        \item \texttt{images/rpi4.build} names them for the image: seven
              programs into \texttt{/bin}, the payload into \texttt{/data}.
        \item \texttt{mkifs} produces \texttt{ifs-rpi4.bin}; the card
              boots it with \texttt{kernel=ifs-rpi4.bin}.
      \end{enumerate}
    \end{column}
    \begin{column}{0.46\textwidth}
      \begin{highlight}
        \textbf{Nothing is mounted, nothing is copied} \\
        The programs and their data live inside the image, so a board run
        can never pick up a stale payload — it is the image or nothing.
      \end{highlight}
      \vskip2mm
      \begin{tech}
        \textbf{The payload is optional by design} \\
        Those build entries are marked optional, so a checkout without the
        generated dataset still builds a bootable image — its payload tests
        report skipped rather than failed. We saw both cases on the board.
      \end{tech}
    \end{column}
  \end{columns}
\end{frame}

\begin{frame}{What the numbers say}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.50\textwidth}
      \begin{table}
        \centering
        \begin{tabular}{@{}rrrr@{}}
          \toprule
          \rtmtablehead{W} & \rtmtablehead{ms/block} & \rtmtablehead{MiB/s} & \rtmtablehead{Speed-up} \\
          \midrule
          1 & 2.278 & 25.12 & 1.00$\times$ \\
          2 & 1.253 & 45.66 & 1.82$\times$ \\
          4 & \num{0.757} & \num{75.55} & \num{3.01$\times$} \\
          \bottomrule
        \end{tabular}
      \end{table}
      \vskip1mm
      {\scriptsize One 64 KiB block, 60\,000-sample recording, measured on
       the board.}
    \end{column}
    \begin{column}{0.46\textwidth}
      \begin{highlight}
        \textbf{Headroom} \\
        One block is 163.84 s of signal at 100 Hz and is sorted in 0.757 ms
        — about \num{216\,000$\times$} real time.
      \end{highlight}
      \vskip2mm
      \begin{itemize}
        \item The plan line is fixed by $n$ and the worker count, so it must
              read the same on any machine — and it does.
        \item \concept{Determinism}: 4 partitions and 2 merge phases every
              run, with the same checksums.
      \end{itemize}
    \end{column}
  \end{columns}
\end{frame}

% ---------------------------------------------------------------------------
\begin{frame}{What did not work, and what it cost}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.48\textwidth}
      \begin{warn}
        \textbf{The short final block} \\
        60\,000 samples do not divide evenly: the last block is 10\,848
        samples in a 16\,384-slot buffer. Everything downstream must respect
        the descriptor's count, and the padding is what keeps the checksum
        from depending on stale memory.
      \end{warn}
      \vskip2mm
      \begin{warn}
        \textbf{A payload-less image} \\
        Built without the dataset, the image still boots and the suites still
        run; the two real-data tests report skipped. It is a build
        configuration, not a failure — but it has to be read correctly.
      \end{warn}
    \end{column}
    \begin{column}{0.48\textwidth}
      \begin{tech}
        \textbf{Distrust inherited from the dataset} \\
        The outlier flags in the dataset are the \emph{injected} mask, not a
        detector's output. Nothing in this service claims to have found an
        outlier by looking at the data.
      \end{tech}
      \vskip2mm
      \begin{tech}
        \textbf{What is still open} \\
        The two programs that talk, and the filter between them. The
        protocol half of the notification is written and tested; the wiring
        is not.
      \end{tech}
    \end{column}
  \end{columns}
\end{frame}

\section{Use Cases and Closing}
% ===========================================================================

\begin{frame}{Where this applies}
  \begin{columns}[t, onlytextwidth]
    \begin{column}{0.48\textwidth}
      \begin{itemize}
        \item \concept{Battery management} — the workload came from battery
              recordings: continuous voltage and current, where spikes are
              measurement artefacts and the median is the part that survives.
        \item \concept{Industrial telemetry} — a plant's sensors stream faster
              than a control loop can afford to sort; offloading to a worker
              pool keeps the collector simple.
        \item \concept{Edge gateways} — a Pi-class board on a real-time kernel
              can sort and clean a channel's history on demand.
      \end{itemize}
    \end{column}
    \begin{column}{0.48\textwidth}
      \begin{itemize}
        \item \concept{Automotive logging} — bursty diagnostic data, where a
              fixed 64 KiB unit and a checksum travel well over a message bus.
        \item \concept{Flight and plant recorders} — the same shape: a time
              series that must be summarised, and an answer that must be
              provably the same every time it is computed.
      \end{itemize}
      \vskip2mm
      \begin{highlight}
        The pattern generalises to any stream where the work is a
        \textbf{fixed-size unit} and the answer must be \textbf{reproducible}.
      \end{highlight}
    \end{column}
  \end{columns}
\end{frame}

              never a whole file.
        \item The sort is parallel, stable and \concept{deterministic} — the
              answer does not depend on the machine.
        \item \concept{3.01$\times$} on four cores, 216\,000$\times$ real

              client never polls.

              board first: \num{1418} checks, clean on host and target.
        \item Checksums are the same across the two file layouts and across
              machines, which is what makes the evidence comparable.
        \item Next: the client and the server talking, and the median filter
